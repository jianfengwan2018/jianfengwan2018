# 版本管理规范

## 原则

继续使用 `jianfengwan2018/jianfengwan2018` 原仓库。Git 提交记录每次有意义的修改；版本标签固定可恢复的节点；版本记录说明这一版改了什么。同一功能版本可以有多个时间快照。

旧提交与旧归档目录保留，不删除、不重写历史、不强制推送。过去的提交标题不补改，今后的提交遵守下面的规则。已有的日期目录是历史归档，不需要为每次开发再复制一个全项目目录。

## 版本号、时间与提交

- **功能版本**：保留现有 `v6`、`v12`、`R25` 的历史称呼，不伪造新的对应关系。
- **快照时间**：使用 UTC，例如 `20261105T104733Z`。同一版本后来再保存时使用新的准确时间；不覆盖旧快照。
- **GitHub 提交**：`archive_commit` 指本仓库固定提交。
- **原托管源提交**：`source_commit` 指原站点源仓库，可能不能在本 GitHub 仓库查询。二者分开保存。
- **标签**：推荐 `html5-v12-20261105T104733Z` 这样的格式；未来正式语义化版本可采用 `v0.1.0-20261109T120000Z`，其中示例不代表已经发布。
- 现有清单时间取自归档提交，明确标为 `archived_at`，不能冒充实际构建时间。

`releases/index.json` 是统一索引，`CHANGELOG.md` 是面向读者的记录。仅有上传的部分 blob、构建文件或线上版本都不算 GitHub 归档完成。

## 日常开发

1. 从最新 `main` 建短期分支，如 `feature/lab-interaction`、`fix/map-collision`。
2. 一个提交只处理一个清楚的目的，避免 `Add files via upload` 等无说明标题。
3. 提交格式：`类型(范围): 内容`，例如 `feat(lab): add electrolysis setup`、`fix(map): repair west road collision`、`docs(releases): index archived versions`。常用类型有 `feat`、`fix`、`docs`、`test`、`chore`。
4. 运行相关测试，记录通过、失败与未运行的项目；代码和资源保持同一个可复现提交。
5. 推送后核对远端提交；需要审阅的改动先开草稿 PR，再按授权合并。小型文档整理可在授权后直接追加到 main。
6. 不把 `.env`、凭据、个人账号配置或私有托管配置作为程序资源上传。

## 完成一个版本

1. 完整源码、运行资源及清单先在同一个分支中准备。R25 在文件齐全前保持 `pending_archive`，不从 v12 复制一份改名充数。
2. 根据清单校验文件，并运行这一版相关的测试。检查需要的图片、音乐、JSON 等资源是否遗漏。
3. 追加有意义的提交，使用正常快进更新；如果 main 在准备期间变化，先读取新头并合并最新内容，不能用旧整树覆盖。
4. 更新版本清单及 CHANGELOG，填入准确的本仓库提交。归档提交中尚不能自引用自身 SHA 时，在随后的小型记录提交中补齐。
5. 在已经核验的归档提交上建立带注释标签，再将该标签推到原仓库。标签一旦发布不移动；修正发布用新时间戳。
6. 如需 GitHub Release，绑定已经存在的标签，写清变更、资源和测试边界。Release 与网站部署分别核对。

标签操作示例（仅在确认目标提交后执行）：

```sh
git tag -a html5-v12-20261105T104733Z 7e678eaa4297867fa715d7b47fc2a60931a8b7d9 -m 'HTML5 v12 archived 2026-11-05T10:47:33Z'
git push origin refs/tags/html5-v12-20261105T104733Z
```

本次整理没有创建远端 tag 或 Release；以上是待执行示例，不是完成记录。创建成功并从远端核对后，才把清单的 `tag` 从 `null` 改为实际标签。

## 后续目录安排

后续只维护原仓库 `chemistry-lab-game` 内的同一个项目，程序文件使用固定路径更新；同一程序的不同时间点由 Git 提交、时间戳记录和核验后的标签区分，不再新建 `html5-complete-map-r25-日期/` 等整套程序快照目录，也不另造程序或仓库。完整 R25 文件就绪后，应对齐原项目的固定文件路径再一次提交，不能用新文件夹来代替版本控制。

已经存在的 Godot 文件和 `web-demo/html5-v6-*`、`web-demo/html5-v12-*` 历史归档暂时保留，避免破坏原版；保留这些旧目录不意味着以后继续复制日期目录。当前不把旧 v12 改名为 R25，也不建立指向旧 v12 的 `latest` 或 `current` 别名。

地图资料归档与可运行游戏版本分别登记。源图、压缩查看副本、分卷及游戏实际使用的资源不能混为一个版本。

## 恢复旧版

先提交或另存本地工作，再在另一个目录检出固定提交，避免覆盖当前工作区：

```sh
git worktree add --detach ../chemistry-v12 7e678eaa4297867fa715d7b47fc2a60931a8b7d9
```

进入该目录的 `chemistry-lab-game/web-demo/html5-v12-roads-pass-2026-11-05`，按其 README 运行。恢复旧版不需要删除 main 或强制重置远端。

## 校验范围

```sh
python3 chemistry-lab-game/tools/check_versions.py
python3 -m unittest discover -s chemistry-lab-game/tools -p 'test_*.py'
```

默认校验完整工作区内归档清单所列文件的字节数、SHA-256 和 Git blob SHA。Godot 初始节点通过历史提交恢复，不在这些 HTML5/地图清单的校验范围内。

也可传 `--tree-json tree.json`，检查 GitHub 递归树响应中的 blob SHA 与大小是否匹配。该模式要求树未截断，且对应本次清单审计的提交或其根 tree SHA；它只核对远端对象元数据，不等价于下载并重算二进制文件 SHA-256。它同样需要本地的版本与地图清单。

校验器不联网、不上传、不修改归档、不创建标签。未归档条目单独报告，不会当作已通过的发布版本。
